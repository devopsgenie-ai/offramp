# Agent operating contract

Read this file before writing anything in this repository. It applies to humans and to
coding agents equally; where it says "you", it means whoever is making the change.

## The one-paragraph version

Nothing is implemented until an RFC for it is accepted. Everything the tool emits is
declarative configuration. Detectors and renderers are pure functions with golden tests.
When the tool does not know something, it records a gap instead of guessing.

## 1. The RFC gate

**No implementation lands without an accepted RFC.** This is enforced in CI, not just by
convention — see `scripts/check_rfcs.py` and `.github/workflows/rfc.yml`.

- A change to `src/`, `schemas/`, `templates/` or `skills/` MUST reference an RFC with
  `status: accepted` in its pull-request body, as `RFC-0001` (four digits).
- Everything under `skills/` is program text, its Markdown included. `SKILL.md` instructs
  the model and is not documentation, so the `.md` exemption below does not reach it.
- Changes to docs, tests for existing behaviour, CI, typo fixes and dependency bumps do
  not need an RFC.
- If you are unsure whether your change needs one, it needs one. Write it; RFCs are
  cheap and rejection is a normal outcome.
- Disagreeing with an accepted RFC is legitimate. Supersede it with a new RFC. Do not
  quietly implement something different from what was accepted — that is the one failure
  mode this process exists to prevent.

See `rfcs/README.md` for the lifecycle and how to write one.

## 2. The declarative constraint

`offramp` is a **code author, not a deployer**.

You MUST NOT add code that:

- runs `kubectl apply|create|delete|patch|edit`, `terraform apply|destroy|import`,
  `helm install|upgrade|uninstall|delete`, or `argocd app sync`
- calls a cloud provider SDK or CLI in a way that creates, modifies or deletes a
  resource — no `boto3` client construction for mutation, no `gcloud`, no `az`
- requires cloud credentials to produce its output
- reads from the network during generation

Read-only operations for *validation* are permitted and encouraged: `terraform validate`,
`kubeconform`, `helm template`, `kustomize build`, `docker build`. These check the output
without touching anything real.

Work that genuinely cannot be declarative — a database dump and restore, a DNS cutover, a
secret value being set for the first time — is **written into a generated runbook for a
human to execute**. It is never executed by this tool.

This constraint is what makes the output reviewable, testable, and safe to run against a
repository you do not own. Do not weaken it for convenience. If you believe a case
requires an exception, that is an RFC.

## 3. Determinism

Detectors and renderers are pure functions.

- Same input repository, same generated bytes. No timestamps, no UUIDs, no random
  ordering, no reading the clock or the environment inside a renderer.
- Iterate collections in sorted order. Serialise mappings with stable key order.
- All I/O happens at the edges — reading the source repo, writing the output tree. The
  middle is data in, data out.
- `apply` is a pure function as well:
  `(appspec, plan, answers, accepted_resolves, accepted_overrides, now) -> answers'`.
  The clock is an argument supplied at the edge, never read inside.
- **No model calls.** A detector or renderer that asks an LLM is not a pure function, and
  it would need network access and an API key to produce output — both already forbidden
  by the declarative constraint above. Judgement comes from an agent *outside* the tool,
  which resolves gaps and writes answers back into the AppSpec. `offramp` is called by a
  model; it never calls one.

Determinism is not stylistic. It is the precondition for golden-file tests, and those are
the only way we can measure whether the tool is getting better.

## 4. Never emit secrets

The tool reads repositories that contain `.env` files, hardcoded tokens, and connection
strings with passwords in them. It must never copy a secret *value* into generated
output.

- Emit a **reference** — an `ExternalSecret`, a `secretKeyRef`, a Terraform data source —
  and record the required key in the gap report.
- When a detector finds a literal credential in the source, record it as a gap with high
  severity so the human is told, and never carry the value forward. That gap MUST tell the
  user to **rotate the credential before cutover**, naming the key and the file it was found
  in. Committed credentials are the normal case in these repositories, not the exception, and
  a migration is the moment when rotating costs least.
- Never write a secret value into a fixture, a test, a log line, or an error message.
- **Never into the answers file.** It is committed to the user's repository. `apply` rejects
  any entry targeting an `EnvVar` whose `sensitive` flag is true. An answer may say where a
  secret comes from; never what it is.

## 5. Gaps over guesses

When the tool cannot determine something, it emits a typed gap: what is missing, why it
matters, a proposed default, and a confidence level. It does not silently invent a value.

Gap count and severity are the project's primary quality metric. A release that resolves
more inputs automatically — turning gaps into confident answers — is a better release.
Track this rather than lines of code.

## 6. Vocabulary

Use these terms precisely; they are the shared language of the codebase and the RFCs.

| Term | Meaning |
|---|---|
| **Scenario** | A source platform we can ingest, e.g. Emergent, Lovable, Vercel. |
| **Detector** | Reads a repository and contributes facts to the AppSpec. One per concern. |
| **AppSpec** | The intermediate representation. Everything detected, nothing rendered. |
| **Renderer** | Turns an AppSpec into files for one target, e.g. Kustomize, Terraform. |
| **Target** | Where config is being generated for, e.g. Kubernetes, Terraform/AWS. |
| **Gap** | Something the tool could not determine, typed and reported. |
| **Fixture** | A checked-in sample app used as a golden test input. |
| **Plan** | A typed, schema-validated changeset proposing AppSpec values. Data, never an action — the model's only output. |
| **Answers file** | `answers.json`: the accumulated, accepted result of applied plans, committed to the app repository. A deterministic input to `scan`. |
| **Skill** | The distribution surface: an instruction file that orchestrates, plus scripts that decide. |

Detectors never write files. Renderers never read the source repository. If you find
yourself wanting to break either rule, the AppSpec is missing a field.

## 7. Before you open a pull request

Run the checks locally. They are the same ones CI runs:

```bash
make check
```

Every pull request must state which RFC authorises it, or why it is exempt. The pull
request template asks for this.

## 8. Repository layout

```
skills/offramp/scripts/   the product: scan, audit, fix, verify, and their modules
  detect/                 detectors, one per concern, including the migration replay
  checks/                 audit checks, one per concern
fixtures/                 golden inputs, their truth.yaml, and expected_* trees
tests/                    unit and golden tests
scripts/                  process tooling: the RFC gate, fixture and behaviour checks
docs/research/            research behind RFC decisions, published in aggregate only
rfcs/                     the RFC process and all design documents
.github/                  CI, templates, code owners
ROADMAP.md                what we intend to build, by track
```

`offramp` has two tracks over one shared core
([RFC-0005](rfcs/0005-two-tracks.md)). Know which one you are changing:

| Area | What it is | Paths, under `skills/offramp/scripts/` unless stated |
|---|---|---|
| **Core** | Shared by both tracks. A change here needs the agreement of both. | `spec.py`, `gaps.py`, `walk.py`, `scan.py`, `report.py`, `rls.py`, `verify.py`, `detect/`; `fixtures/*/expected_bare/`, `truth.yaml`, `gap_count.json`; `scripts/check_fixtures.py`, `scripts/check_rfcs.py` |
| **Auditor** | `audit` and `fix` | `audit.py`, `audit_report.py`, `findings.py`, `fix*.py`, `checks/`; `fixtures/*/expected_audit/`, `expected_fix/`, `behaviour.yaml`; `scripts/check_fix_behaviour.py`; `docs/research/` |
| **Generator** | `render`, and later `show`, `apply` and the skill | `render.py`, `render/`, `fixtures/*/expected_render/` |

The AppSpec is core. A field one track needs is added under that track's RFC and
reviewed as a core change. Every pull request keeps both tracks' golden files green.

`src/`, `schemas/` and `templates/` do not exist. The RFC gate still covers them, so
creating one needs an accepted RFC like any other implementation change.
